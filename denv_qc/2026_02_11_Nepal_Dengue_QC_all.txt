For Illumina MiSeq amplicon data like this, I'd recommend fastp for a few reasons:

  - All-in-one: Does both QC assessment and adapter/quality trimming in a single pass, whereas FastQC is assessment-only (you'd still need a separate trimmer like Trimmomatic)
  - Speed: Significantly faster than FastQC + Trimmomatic pipeline
  - Auto-detects adapters: No need to manually specify Illumina adapter sequences
  - Good reports: Generates HTML + JSON reports per sample
  - MultiQC compatible: The JSON output can be aggregated across all 40 samples with MultiQC for a single summary view

  My recommended workflow would be:
  1. fastp - trim adapters, filter low-quality reads, generate per-sample QC reports
  2. MultiQC - aggregate all 40 fastp reports into one summary for easy comparison across samples/serotypes

  This is especially practical here since these are viral amplicon libraries (small genome, MiSeq) where you'll want clean reads for downstream consensus/variant calling anyway — so combining QC + trimming saves
  a step.

  Overall QC Results:
  - All samples pass with Q20 > 98% and Q30 > 94% — excellent quality
  - Read retention after trimming ranges from 73.5% to 91.9% (mostly adapter removal)
  - GC content is consistent at ~46-51%, expected for Dengue virus

Problem: Very short insert size
2x231bp MiSeq
The insert size distribution peaking at 38-50bp means the library fragments are extremely short — much shorter than the read length. This is consistent with:

  - Degraded clinical RNA — these are plasma samples from dengue patients, where viral RNA is often fragmented
  - PCR amplicon tiling with short overlaps — if they used a tiling amplicon approach, the amplicons may have been short by design
  - Over-fragmentation during library prep

  The practical consequence: R1 and R2 overlap extensively (a 50bp insert sequenced 2x231bp means each read extends ~180bp past the insert into adapter). This explains the ~15-20% read loss during trimming — it's
   largely adapter read-through removal.

Problem: The R2 N-Content Spikes — MiSeq Cycle-Specific Imaging Failures

  This is a flowcell-level instrument artifact during Read 2 sequencing. Here's the evidence:

  - Affects ALL 40 samples identically (40/40 at positions 24, 59, 82; 27/40 at position 131)
  - R1 is completely clean at the same positions
  - Single-cycle events: the spike is exactly 1 base wide, with quality plummeting to Q13-17 at the spike and recovering over ~5 cycles afterward
  - The recovery pattern (Q14 → Q29 → Q34 → Q36 over 3-4 bases) is classic post-failure phasing recovery

  What happened: During specific cycles of Read 2, the MiSeq instrument had imaging failures — most likely caused by:

  - Air bubbles passing through the flowcell during those specific cycles
  - Reagent delivery failures at those cycles
  - Focus loss during imaging

  At cycle 25 (R2 pos 24), 42% of all reads across the entire flowcell got N-called. Because this affects all tiles simultaneously, it's a run-level chemistry/fluidics issue, not a sample-specific problem. The
  irregular spacing (35, 23, 49 cycles apart) rules out a periodic mechanical cause and points to stochastic bubble/reagent events.

  Impact Assessment

  The good news: fastp's quality trimming and N-filtering handles this well — the post-filtering data is clean. The N-spike bases get either trimmed or the reads get discarded. The bases flanking the spikes
  recover to Q>30 within 3-5 cycles. This is a cosmetic issue in the raw data that doesn't significantly impact the final trimmed reads.

  Problems for our DENV data specifically

  Given what we found in the fastp QC (short inserts, R2 imaging artifacts, clinical plasma RNA), here are the critical gaps:

  1. fastp defaults are far too permissive
  - Default min quality = Q15, min length = 15bp. We used Q20 and 50bp, which is already conservative for viral WGS. A 15bp read is useless for a 10.7kb genome.
  - No sliding window trimming (--cut_front/--cut_tail) — the R2 imaging artifact bases (Q13-14) would be partially retained
  - No overlap-based error correction — critical for our data given the 38-87bp inserts where R1/R2 overlap extensively
  - No N-filtering — the R2 cycle failures (up to 42% N at positions 24, 59, 82) need explicit handling

  2. No primer/amplicon trimming
  - These are PCR-amplified WGS libraries. If amplicon primers were used, there is no ivar trim step to remove primer sequences, which would introduce false variants at primer binding sites.

  3. No duplicate marking/removal
  - Our data shows 4-21% duplication rates. PCR duplicates can bias variant frequencies and inflate coverage estimates. No samtools markdup or Picard MarkDuplicates step exists.

  4. No mapping quality filtering
  - samtools view runs with no -q or -F flags — unmapped reads, low-MAPQ reads, supplementary alignments all pass through to variant calling. With clinical plasma samples that likely contain host reads, this is a
   problem.

  5. GATK ploidy = diploid (wrong for virus)
  - bcftools call correctly uses --ploidy 1 but the main GATK HaplotypeCaller pathway uses the default ploidy of 2, which will model heterozygous calls that don't exist in a haploid viral genome.

  6. No VCF filtering
  - Raw GATK output goes straight to SnpEff annotation with no VariantFiltration or bcftools filter step. No strand bias, read depth, or quality-by-depth filters.

  7. ivar -t 0 is risky
  - A frequency threshold of 0 means the consensus base is called at any frequency. With our samples potentially containing host reads or mixed infections, this could call incorrect bases at low-coverage
  positions.

  8. No genome coverage assessment
  - Only reports average depth — no metrics for % genome covered at 10x, 30x, 100x. A sample could have 500x average but 0x over 20% of the genome and still look fine.

  Recommended changes

  SHOULD ADD:
    + Stricter fastp params: -q 20, --length_required 50,
      --cut_front, --cut_tail, --cut_window_size 4,
      --cut_mean_quality 20, --correction, --overlap_len_require 30
    + samtools markdup or picard MarkDuplicates
    + samtools view -F 0x904 -q 20 (filter unmapped, secondary,
      supplementary, and low MAPQ reads)
    + ivar trim (if primer BED file is available)
    + ivar consensus -t 0.5 -m 20 (majority-rule at 50%, min 20x)
    + GATK --ploidy 1
    + GATK VariantFiltration or bcftools filter
    + Genome coverage breadth metrics (% at 10x, 30x, 100x)
    + Programmatic evaluation of FastQC/fastp reports (pass/fail gate)

  SHOULD CHANGE:
    ~ fastp defaults → explicit parameters matching our QC settings
    ~ ivar -t 0 → -t 0.5 (or at least 0.25 for mixed infection detection)
    ~ ivar default min depth → explicit -m 20 or -m 30
    ~ samtools mpileup -d 1000 → -d 10000 (for high-coverage amplicon data)

  COULD REMOVE:
    - sam2consensus_test2.py / sam2consensus_test2_ivar.py
      (redundant/unused development scripts that cause confusion)

  The pipeline provides a reasonable skeleton but needs hardening for production use with clinical amplicon data like ours. The biggest risks are the permissive fastp defaults (which would fail to clean up our R2
   artifacts), missing duplicate removal, and the wrong ploidy setting in GATK.
